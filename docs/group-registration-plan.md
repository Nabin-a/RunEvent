## 2. หลักการออกแบบ (จาก mockup)

1. **ผู้สมัครและระยะ (ขั้นเดียว):** เริ่มที่การ์ดคนที่ 1, ปุ่ม "+ เพิ่มผู้สมัคร" (ไม่เกินเพดานต่อครั้ง), ยอดรวมแยกตามระยะด้านขวา (มือถือ: แถบติดล่าง); 1 การ์ด = 1 คน (พับ/กาง, ป้าย "กรอกครบ / ยังขาด x หมวด"); บนสุดของการ์ด: **radio "ตัวเอง / คนอื่น"** → คนอื่น = **dropdown เพื่อนที่บันทึกไว้** (รายชื่อพร้อมเพศ/อายุ, "+ เพิ่มคนใหม่") — **ฟอร์มขึ้นหลังเลือกแล้วเท่านั้น**; เลือกแล้วแสดงชื่อพร้อมปุ่ม "เปลี่ยน"; การ์ดที่ "ตัวเอง" ถูกใช้ไปแล้วข้าม radio (ดูตารางข้อ 1); ข้างกันเป็น **dropdown "ระยะ"** (ราคา, "เหลือ x ที่" นับคนในใบนี้แล้ว, ระยะเต็มกดไม่ได้, เตือนเมื่อเหลือน้อย); ใต้ลงมาเป็น 3 หมวดพับ/กาง — **ข้อมูลทั่วไป** (จากโปรไฟล์, รุ่นอายุคำนวณจากวันเกิด ณ วันงาน, ติ๊กบันทึกกลับโปรไฟล์/บันทึกคนใหม่), **ข้อมูลเพิ่มเติม** (คำถามที่ผู้จัดเพิ่ม), **สินค้าที่ระลึก** (เสื้อแข่งด้วยชุดเลือกเสื้อเดิม สต็อกนับรวมทุกคนในใบ + เหรียญ Finisher); หัวหมวดตอนพับสรุปค่าที่กรอกและบอกว่ายังขาดอะไร (ไม่มีป้ายกำกับที่มาของชุดคำถาม เช่น "จากโปรไฟล์" / "ผู้จัดเพิ่ม" — คำสั่งผู้ใช้ 28 พ.ย. 2026); เพิ่ม/ลบคนได้
2. **รับอุปกรณ์:** เลือกครั้งเดียวใช้ทั้งกลุ่ม; ส่งไปรษณีย์ = ที่อยู่เดียว ค่าส่งต่อคำสั่งซื้อ
3. **ของที่ระลึก (ร้านค้า):** เป็นของคำสั่งซื้อ ไม่ผูกกับคนใดคนหนึ่ง (ผู้จัดย้ายตำแหน่งขั้นได้เหมือนเดิม)
4. **สรุปและชำระ:** ตารางรายคน (ระยะ เสื้อ ค่าสมัคร) + ยอดรวม; ผู้ซื้อยอมรับกติกาแทนทุกคนและยืนยันว่าได้รับความยินยอมจากผู้สมัครคนอื่น; จ่ายครั้งเดียว
5. **สมัครคนเดียว = เส้นทางเดียวกัน** (การ์ดเดียว) — ไม่มีฟอร์มสองแบบ

## 3. กฎธุรกิจที่ต้องรักษา (AGENTS.md ข้อ 4)

- ผู้ซื้อ ≠ ผู้เข้าร่วม: ผู้ซื้อ = บัญชีที่กดสมัคร; ใบสมัครรายคนเก็บข้อมูลผู้เข้าร่วมของตัวเอง
- ราคาคำนวณฝั่งเซิร์ฟเวอร์ต่อคน (ราคาช่วงเวลา ณ ตอนสั่ง) เก็บ snapshot ต่อใบ; เงินเป็นสตางค์จำนวนเต็ม
- โควตาระยะ / โควตารวม / สต็อกเสื้อ / ของที่ระลึก กันแบบ atomic **ทั้งคำสั่งซื้อในธุรกรรมเดียวตอนกดชำระ** — ได้ครบทุกคนหรือไม่ได้เลย (ไม่จองบางคน); ไม่กันที่นั่งระหว่างกรอก ถ้าเต็มระหว่างนั้น ตอบกลับว่าการ์ดคนที่เท่าไรต้องเปลี่ยนระยะ/ไซส์ และข้อมูลที่กรอกไม่หาย
- เวลาหมดอายุการจองใช้ร่วมทั้งคำสั่งซื้อ หมดเวลา = คืนทุกที่นั่งในคำสั่งซื้อ
- ผลชำระยืนยันจาก provider (Local: จำลอง Webhook) แบบ idempotent ต่อคำสั่งซื้อ; รายการมาช้าหลังหมดเวลาใช้กติกาเดิม (คืนเงิน/รอตรวจ)
- คืนเงินรายคน ไม่เกินยอดของคนนั้น; ไม่แก้หรือลบรายการเงินเดิม
- กติกางานและความยินยอม PDPA เก็บเวอร์ชันที่ยอมรับในทุกใบ

## 4. แผนแบ่งช่วง

### ช่วง 0 — template การ์ดผู้สมัคร (ทำก่อนตามคำสั่งผู้ใช้ "เริ่มเลย" 28 พ.ย. 2026) — พัฒนาแล้ว ยังไม่ commit
- ส่วนระบบ "เสื้อที่ระลึก" เลิกเป็นส่วนแยกของขั้นตอนสมัคร: `CORE_BLOCKS` เหลือ 5 ส่วน, "ข้อมูลผู้สมัคร" ต้องอยู่หลัง "เลือกระยะ" (ไซส์เสื้อใช้ระยะ), ลำดับเริ่มต้นเป็น เริ่ม → ข้อมูล → (ขั้นของผู้จัด) → ของที่ระลึก → ที่อยู่ → สรุป
- ฟอร์มที่บันทึกไว้ก่อนหน้า (ฉบับใช้งาน / ร่าง / ฉบับเก่าที่กู้คืน) ผ่าน `withoutRetiredBlocks()`: ขั้นที่มีแต่เสื้อหายไป เว้นแต่ผู้จัดใส่คำถามไว้ (เหลือเป็นขั้นของผู้จัด) — ไม่ต้องแก้ฐานข้อมูล
- หน้าสมัคร (`RegistrationLabView`): radio "สมัครให้ตนเอง / สมัครให้ผู้อื่น" → ผู้อื่น = dropdown "สมัครให้ใคร" (เพื่อนที่บันทึกไว้ + "+ เพิ่มคนใหม่") แทนแท็บ + การ์ดเพื่อน → ฟอร์มขึ้นหลังเลือก; ไม่มีเพื่อนที่บันทึกไว้ = ฟอร์มขึ้นเลย; ข้อมูลเพื่อนแก้ในฟอร์มได้เลย (ไม่ต้องเปิดหน้าต่างแก้ไข) และถูกบันทึกกลับรายชื่อเพื่อนตอนสมัครเหมือนเดิม
- ฟอร์มแบ่ง 3 หมวดพับ/กาง (`<details>`): ข้อมูลทั่วไป (ชื่อ, ข้อมูลส่วนตัวและเอกสาร, ผู้ติดต่อฉุกเฉิน), ข้อมูลเพิ่มเติม (คำถามของผู้จัดในขั้นนี้), สินค้าที่ระลึก (เสื้อแข่งด้วย `ShirtGallery` เดิม + เหรียญ/เสื้อ Finisher); หัวหมวดสรุปค่าที่กรอก + "✓ ครบ / ยังไม่ครบ / ยังไม่เลือกไซส์เสื้อ"; หมวดที่ยังไม่ครบเปิดไว้ตอนเริ่ม; กดถัดไปแล้วมีปัญหา = หมวดที่มีปัญหาเปิดเองและเลื่อนไปช่องนั้น; เปลี่ยนผู้สมัคร = ล้างคำตอบและไซส์เสื้อ
- `SelectMenu` รองรับหัวกลุ่ม (`group`) และบรรทัดรอง (`hint`)
- ตรวจ: typecheck, build เว็บ/คอนโซล, สคริปต์กฎขั้นตอน 50 ข้อผ่าน (รวมกรณีฟอร์มเก่ามีเสื้อ), สถานะเผยแพร่ 17 ข้อผ่าน; เบราว์เซอร์ (บัญชีนักวิ่ง งานแหลมพรหมเทพ ไม่ได้ส่งใบสมัคร): ขั้นเหลือ เริ่ม/ข้อมูล/ของที่ระลึก/ที่อยู่/สรุป/ชำระเงิน, ยังไม่เลือกว่าให้ใคร = ไม่มีฟอร์ม, ตนเอง = 3 หมวดพร้อมข้อมูลโปรไฟล์, พับทุกหมวดแล้วกดถัดไป = หมวดที่ขาดเปิดและโฟกัสช่องผู้ติดต่อฉุกเฉิน, กรอกครบแต่ไม่เลือกไซส์ = "กรุณาเลือกไซส์เสื้อตามสิทธิ์สมัคร" และหมวดสินค้าที่ระลึกเปิด, เลือกไซส์แล้วไปขั้นของที่ระลึกได้, ผู้อื่น = dropdown เพื่อน 2 คน + เพิ่มคนใหม่ เลือกแล้วฟอร์มเติมข้อมูลเพื่อน, เปลี่ยนเป็นคนใหม่ = ฟอร์มว่างและไซส์ถูกล้าง, มือถือ 375px ไม่ล้น; ลบประวัติเข้าสู่ระบบจากการทดสอบ เบราว์เซอร์กลับเป็นผู้เยี่ยมชม
- ทดสอบ API การเผยแพร่ (ปรับตามกฎใหม่ 28 พ.ย.) 47/48: ข้อที่ไม่ผ่านคือ "บันทึกฟอร์มด้วยตัวแก้ไขเก่า" ซึ่งตอบ 410 ตั้งแต่รวมตัวแก้ไข (ship 09012dc) — สคริปต์ล้าสมัย ไม่ใช่ปัญหาใหม่ แก้สคริปต์แล้ว
- ยังไม่ได้ตรวจ: ตัวแก้ไขขั้นตอนของผู้จัดในเบราว์เซอร์ (ระหว่างทดสอบบัญชีในเบราว์เซอร์ถูกสลับจากแท็บอื่น), ส่งใบสมัครจริงจนชำระเงินผ่านหน้าเว็บ

### ช่วง 1 — ข้อมูลและเซิร์ฟเวอร์ — พัฒนาแล้ว (28 พ.ย. 2026) ยังไม่ commit
ทำแล้ว:
- `bookOrderInTx()` ใน `server/index.ts`: ตรวจและจองทั้งคำสั่งซื้อในธุรกรรมเดียว; `POST /api/registrations` (คนเดียว) ใช้โค้ดเดียวกันเป็นคำสั่งซื้อ 1 คน รูปแบบผลลัพธ์เดิม

- ใบสมัครในกลุ่ม: `orderCode` เดียวกัน, `orderEntryNo` / `orderEntryCount`, `orderSelfEntry`; ราคาแยกรายคน; ค่าส่งชุดแข่งครั้งเดียวที่คนแรก; ของที่ระลึกผูกกับคนแรก; เวลาจองเดียวกันทั้งใบ
- ตรวจ: เพดานต่อครั้ง `RaceEvent.maxEntriesPerOrder` (ค่าเริ่มต้น 10, เซิร์ฟเวอร์ไม่เกิน 20), "ตนเอง" ไม่เกิน 1 คน, คนเดียวกันซ้ำในใบ (ชื่ออังกฤษ + วันเกิด — เลขบัตรเก็บแบบปิดบางส่วนจึงใช้แยกคนไม่ได้), ติดต่อของเพื่อน, คำถามของผู้จัด, อายุ, ที่นั่งรายระยะ + ทั้งงาน และสต็อกเสื้อรายไซส์โดยนับคนในใบเดียวกัน — ข้อความบอก "คนที่ x:" พร้อม `entryIndex` และ `full: 'category' | 'shirt'`

### ช่วง 4 — หลังสมัคร — พัฒนาแล้ว (28 พ.ย. 2026) ยังไม่ commit
ทำแล้ว:
- หน้าประวัติ: ใบที่มาจากคำสั่งซื้อหลายคนมีป้าย "สมัครมาด้วยกัน x คน · ORD-…"; ในแถวที่กาง "คำสั่งซื้อ ORD-…: รายชื่อทุกคน · ชำระรวมทั้งใบ / ยอดรวมทั้งใบ ฿…"; ปุ่ม "ชำระเงิน" ของใบไหนก็ได้ = หน้าชำระของทั้งใบ (ทุกคน + ยอดรวม) จ่ายครั้งเดียว
- ฝั่งผู้จัด "ผู้สมัคร": ค้นด้วยรหัสคำสั่งซื้อได้ (เห็นทุกคนที่มาด้วยกัน), แถวมี "กลุ่ม x คน", แผงรายละเอียดมี "สมัครมาด้วยกัน" (คนที่ 1..n กดเปิดคนอื่นได้ + หมายเหตุจ่ายครั้งเดียว แต่ละคนมีสิทธิ์ BIB และเงินคืนของตัวเอง), ส่งออก CSV เพิ่มคอลัมน์ "รหัสคำสั่งซื้อ" และ "คนที่ในคำสั่งซื้อ" (1 แถวต่อคนเหมือนเดิม)
- ฝั่งผู้จัด "รายรับและคืนเงิน": คำขอคืนเงินบอก "คำสั่งซื้อ … คนที่ x/n" + หมายเหตุ "คืนเฉพาะคนนี้ คนอื่นไม่เปลี่ยน ค่าจัดส่งไม่คืน"; สมุดรายการเงินแสดงรหัสคำสั่งซื้อ; ยอดนับรายคนเหมือนเดิม (ค่าส่งอยู่ที่คนแรกครั้งเดียว ไม่นับซ้ำ)
- ใบยืนยันทางอีเมล: **ไม่ได้ทำ** — ระบบยังไม่มีการส่งอีเมลจริง (โหมด Local) หน้าสำเร็จและหน้าประวัติแสดงใบยืนยัน/QR ของทุกคนแทน
- QR แยกรายคนในเอกสาร (28 พ.ย. 2026): ผู้ใช้ลองการ์ด QR รายคนบนจอ (แบบ "A") แล้วไม่เอา — ที่ต้องการคือ "กดพิมพ์หรือกดโหลดให้รวมรายการไว้ในตัวเอกสารแบบแยกกัน template เดียวกัน" ตอนนี้ปุ่ม "พิมพ์" / "ดาวน์โหลด" (และ "แชร์" บนเครื่องที่แชร์ไฟล์ได้) ของคำสั่งซื้อหลายคน ทั้งหน้าสมัครสำเร็จและป๊อปอัปใบยืนยันในหน้าประวัติ ได้ใบยืนยันของทุกคนแยกกันคนละส่วนในแบบเดียวกับใบยืนยันคนเดียว (หัว "คนที่ x จาก n", รายการ, QR ของคนนั้น): พิมพ์ = หน้าละคน (`ConfirmationPrintSet` + `.reg-print-set` ใน styles.css), ดาวน์โหลด = รูป PNG ยาวรูปเดียว ต่อกันมีเส้นประคั่น ชื่อไฟล์เป็นรหัสคำสั่งซื้อ (ผู้ใช้เลือกรูปยาวแทน PDF) — `orderConfirmationSheets()` ใน `RegistrationConfirmation.tsx`; การ์ด QR บนจอเอาออกแล้ว หน้าสำเร็จกลับเป็นรายชื่อ + QR เล็กแบบเดิม; การส่ง QR เข้าอีเมล/LINE ของแต่ละคนอัตโนมัติยังทำไม่ได้ (ไม่มีระบบส่งข้อความ)
- ตรวจ: typecheck; สร้างคำสั่งซื้อ 3 คนผ่าน API (งานน่าน) แล้วเปิดในเบราว์เซอร์: นักวิ่งเห็นป้ายและยอดรวม ฿2,302.50 กดจ่ายจากใบที่ 2 ได้หน้าชำระทั้ง 3 คน; ผู้จัด (owner) ค้น ORD-… ได้ 3 แถว "กลุ่ม 3 คน" แผงรายละเอียดแสดงคนที่มาด้วยกัน; ลบใบทดสอบ 3 ใบ log 1 รายการ คืนข้อมูลงานและโปรไฟล์ เบราว์เซอร์กลับเป็นผู้เยี่ยมชม — ยังไม่ได้เปิดดู: หน้ารายรับและคืนเงิน (ต้องมีคำขอคืนเงิน), ไฟล์ CSV จริง

แผนเดิม:
- หน้าประวัติ: ใบที่สมัครมาด้วยกันมีป้าย "สมัครมาด้วยกัน x คน · รหัสคำสั่งซื้อ"; รอชำระ = จ่ายทั้งคำสั่งซื้อ
- ใบยืนยันส่งให้ทุกคนที่มีอีเมล
- ฝั่งผู้จัด: รายชื่อผู้สมัคร/ส่งออก 1 แถวต่อคน + รหัสคำสั่งซื้อ + ตัวกรอง; คืนเงินรายคนแสดงคำสั่งซื้อที่อยู่ด้วย
- รายงานยอด: นับรายคนเหมือนเดิม ไม่นับซ้ำค่าส่ง

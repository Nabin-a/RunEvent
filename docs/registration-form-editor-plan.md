## 2. ส่วน A — หน้ารายละเอียดงานแบบแม่แบบเดียว

### 2.1 โครงหน้า (ข้อเสนอ)

ลำดับคงที่ ส่วนที่งานนั้นไม่มีข้อมูลจะไม่แสดง (กลไกนี้มีแล้ว):

| ลำดับ | ส่วน | ข้อมูลมาจาก |
|---|---|---|
| 1 | หัวหน้างาน: ภาพปก ชื่อ วันที่ สถานที่ | ข้อมูลงาน |
| 2 | เกี่ยวกับงาน + จุดเด่น | `overviewParagraphs`, `highlights` |
| 3 | ระยะและค่าสมัคร (ช่วงราคา เกณฑ์อายุ ที่นั่ง) | ระยะ ราคา โควตา |
| 4 | สิ่งที่ได้รับ + ตารางไซส์เสื้อ | `racePackItems` (รวมไอคอนการ์ด), สต็อกเสื้อ |
| 5 | กำหนดการ | `scheduleItems` |
| 6 | สถานที่และติดต่อผู้จัด | ข้อมูลงาน ข้อมูลองค์กร เวอร์ชันกติกา |
| 7 | ของที่ระลึก | สินค้าของงาน |
| ขวา | การ์ดสมัคร (sticky) | สถานะ ช่วงรับสมัคร ราคา โควตา + ข้อความหัวการ์ด/โปรโมตที่ตั้งไว้ |

### 2.2 ผู้จัดแก้อะไรได้และแก้ที่ไหน

- ข้อความ "เกี่ยวกับงาน / จุดเด่น / สิ่งที่ได้รับ / กำหนดการ" แก้ในเมนูตั้งค่างาน (ตำแหน่งเมนูให้ตรงกับงาน redesign navbar ที่กำลังวาด) ใช้ตัวแก้รายการแบบทีละข้อ ตัวแก้การ์ดพร้อมไอคอน และตัวแก้ไทม์ไลน์ที่ทำไว้แล้ว
- การ์ดสมัคร (หัวการ์ด ข้อความโปรโมต มาสคอต แถบโควตารวม ลิงก์ลัด) ย้ายไปตั้งค่าในเมนูเดียวกัน (ข้อเสนอ — ต้องยืนยัน ข้อ 8)
- ข้อมูลธุรกิจ (ราคา โควตา ระยะ สถานที่) แก้ที่เมนูเดิมเหมือนปัจจุบัน
- เอาเมนู "หน้ารายละเอียดงาน" (ตัวแก้ไขเต็มจอ) ออกจากระบบผู้จัด

### 2.3 ข้อมูลเดิม

- หน้าสาธารณะเลิกอ่าน `detailLayout`, `detailCustomBlocks`, `detailPageDraft`, `detailPageVersions`, `detailPageV` แต่ **ไม่ลบ** ข้อมูลเหล่านี้ออกจาก `detail_json` (ตัดสินใจข้อ 1.3)
- ข้อความที่ตอนนี้อยู่ในชิ้นส่วนของหน้าแบบ v2 ที่เผยแพร่แล้ว ต้องแปลงกลับลงช่องข้อมูลงานครั้งเดียว:
  - บล็อก `core-about`: ชิ้นข้อความ → `overviewParagraphs` (แยกย่อหน้าด้วยบรรทัดว่าง), ชิ้นรายการ → `highlights`
  - บล็อก `core-racepack`: ชิ้นการ์ด → `racePackItems` (เพิ่มช่องไอคอนให้ `racePackItems`)
  - บล็อก `core-schedule`: ชิ้นไทม์ไลน์ → `scheduleItems`
  - แปลงเฉพาะเมื่อบล็อกนั้นยังมีชิ้นส่วนชนิดที่คาดไว้ ถ้าผู้จัดเปลี่ยนโครงไปมาก ให้คงค่าเดิมของงานและรายงานรายการที่แปลงไม่ได้
  - ร่างที่ยังไม่เผยแพร่ (เช่น ร่างงานดอยสุเทพ) ไม่แปลง เก็บไว้เฉย ๆ
- API `PATCH detailPageDraft / detailPagePublish` ปิดรับ (ตอบข้อความว่าใช้เมนูตั้งค่างานแทน) แต่ยังอ่านข้อมูลเดิมได้สำหรับ Platform Owner

### 2.4 เกณฑ์เสร็จ

- ทุกงานแสดงหน้าตามโครงข้อ 2.1 รวมงานที่เคยจัดหน้าเอง
- ข้อความที่ผู้จัดแก้ไว้ในหน้าแบบ v2 ที่เผยแพร่แล้วยังแสดงครบหลังแปลง
- ไม่มีเมนูหรือ API ที่ยังแก้โครงหน้ารายละเอียดได้
- ข้อมูลหน้าเดิมยังอยู่ในฐานข้อมูล (ตรวจด้วยการอ่านค่า)

## 3. ส่วน B — ตัวแก้ไขฟอร์มสมัครแบบลากวาง

### 3.1 นำอะไรจากตัวแก้ไขหน้าเดิมมาใช้

คลังชิ้นส่วน, โครงหน้าแบบต้นไม้, ตัวอย่างใน iframe (เดสก์ท็อป/มือถือ), ลากวางในตัวอย่างพร้อมสำเนาที่ถือ, แก้ข้อความในตัวอย่าง (ดับเบิลคลิก/F2), เมนูคลิกขวา, Shift/Ctrl+คลิกเลือกหลายรายการ, ย้อนกลับ/ทำซ้ำแบบรวมเป็นขั้นเดียว, ร่าง → ตัวอย่าง → เผยแพร่ → ฉบับย้อนหลัง, ตัวแก้รายการแบบทีละข้อ

งานเตรียม: แยกส่วนที่ใช้ร่วมออกจาก `EventPageEditor.tsx` (ราว 2,900 บรรทัด) เป็นโมดูลกลางก่อน แล้วตัวแก้ไขฟอร์มใช้โมดูลนั้น

### 3.2 ความหมายของชิ้นส่วนในฟอร์ม

| ตัวแก้ไขหน้า (เดิม) | ตัวแก้ไขฟอร์ม |
|---|---|
| บล็อก | ขั้นตอนของฟอร์ม (`RegistrationStepDef`) — ลำดับขั้นตอนคงที่ ผู้จัดเปลี่ยนไม่ได้ |
| ชิ้นส่วน | คำถาม (`CustomRegistrationField`) หรือชิ้นเนื้อหา (หัวข้อย่อย ข้อความอธิบาย ภาพ) |
| ชิ้นข้อมูลงาน | ช่องหลักของระบบ (ชื่อ เลขบัตร วันเกิด ระยะ ไซส์เสื้อ ผู้ติดต่อฉุกเฉิน ยอมรับกติกา) ตามนโยบายสิทธิ์ |

ผู้จัดวางคำถามและเนื้อหาได้ในพื้นที่ที่ขั้นตอนนั้นอนุญาต (ข้อเสนอ: ส่วน "ข้อมูลเพิ่มเติม" ของแต่ละขั้นตอน) ช่องหลักเรียงตามแม่แบบของแพลตฟอร์ม

### 3.3 ประเภทคำถาม

มีแล้วในโมเดลข้อมูล (`CustomFieldType`): ข้อความสั้น (`text`), ข้อความยาว (`textarea`), อีเมล, เบอร์โทร, ตัวเลข, วันที่, ดรอปดาวน์ (`select`), เลือกข้อเดียว (`radio`), ติ๊ก (`checkbox`), เลือกหลายข้อ (`multiselect`), อัปโหลดไฟล์, เลือกจากภาพ (`image_choice`), ที่อยู่ — ส่วน `size_selector` และ `distance_selector` เป็นช่องหลักของระบบ ผู้จัดไม่สร้างเอง

เสนอเพิ่มในรอบที่ 2: เวลา (`time`), สเกลคะแนน 1–5 / 1–10 (`scale`)

### 3.4 การตั้งค่าคำถาม (แผงขวา)

- หัวข้อคำถาม (แก้ในตัวอย่างได้), คำอธิบาย, placeholder
- สวิตช์ "บังคับตอบ" — คำถามที่บังคับแสดง * ในตัวอย่างและหน้าสมัครจริง
- เปลี่ยนประเภทคำถาม: แปลงได้ระหว่างประเภทที่เข้ากันและเก็บตัวเลือกไว้ (`radio` ↔ `select` ↔ `multiselect`, `text` ↔ `textarea`) ข้ามกลุ่มต้องยืนยันก่อน
- ตัวเลือกคำตอบแบบแถว (เพิ่มด้วย Enter, ลากสลับ, วางหลายบรรทัด) และตัวเลือก "อื่น ๆ (ระบุ)"
- ตรวจคำตอบ (พับได้): ความยาว, ช่วงตัวเลข, รูปแบบสำเร็จรูป (อีเมล เบอร์มือถือ เลขบัตร), "เลือกอย่างน้อย/อย่างมาก N ข้อ" สำหรับเลือกหลายข้อ, ชนิดและขนาดไฟล์, ข้อความเตือนเมื่อผิด
- "ข้อมูลอ่อนไหว" (`isSensitive`) — ติ๊กแล้วคำถามนั้นต้องรอ Platform Owner อนุมัติก่อนเผยแพร่ และซ่อนจากเจ้าหน้าที่หน้างาน
- แสดงเฉพาะบางระยะ (`visibilityCondition` ตามระยะที่เลือก) — รอบแรก; เงื่อนไขตามคำตอบข้ออื่นเป็นรอบที่ 2

### 3.5 กติกาที่ต้องบังคับ (หน้าจอและเซิร์ฟเวอร์)

| กรณี | กติกา |
|---|---|
| ช่อง `LOCKED` | บังคับตอบเสมอ ลบ ซ่อน เปลี่ยนประเภทไม่ได้ |
| ช่อง `CONFIGURABLE` | เปิด/ปิดบังคับตอบได้ เปลี่ยนประเภทไม่ได้ |
| คำถามที่ผู้จัดสร้าง (`CUSTOMIZABLE`) | ปรับได้ทุกอย่างจนกว่าจะมีคนตอบ |
| คำถามที่มีคนตอบแล้ว | เปลี่ยนประเภทไม่ได้, ตัวเลือกที่มีคนเลือกแล้วซ่อนได้แต่ลบไม่ได้, ลบคำถามไม่ได้ (ซ่อนได้) |
| เปลี่ยน "บังคับตอบ" | มีผลกับเวอร์ชันฟอร์มใหม่เท่านั้น ใบสมัครเก่าไม่ต้องกรอกเพิ่ม |
| เผยแพร่ | ได้เวอร์ชันฟอร์มใหม่ (immutable) ใบสมัครเก็บเวอร์ชันที่ใช้ |
| ส่งใบสมัคร | เซิร์ฟเวอร์ตรวจบังคับตอบและการตรวจคำตอบตามเวอร์ชันของใบสมัครนั้น เฉพาะคำถามที่แสดงจริงตามเงื่อนไข |
| สิทธิ์ | owner / event_manager แก้ได้, staff ดูอย่างเดียว, ข้ามองค์กรไม่ได้ (ตอบ 403) |
| ห้ามเด็ดขาด | คำถามขอรหัสผ่าน ข้อมูลบัตรชำระเงิน หรือ token (ตามข้อ 17.6) |

ราคา ส่วนลด และโควตายังคำนวณ/กันที่นั่งฝั่งเซิร์ฟเวอร์ ไม่อาศัยคำตอบในฟอร์ม

### 3.6 หน้าจอและสถานะที่ต้องออกแบบ

ฟอร์มว่าง, กำลังโหลด, บันทึกไม่สำเร็จ, ไม่มีสิทธิ์, คำถามรออนุมัติ (ข้อมูลอ่อนไหว), เผยแพร่ไม่ได้เพราะข้อมูลไม่ครบ, งานปิดรับสมัครหรือถูกระงับ — และโหมด "ลองกรอก" ในตัวอย่างที่ตรวจคำตอบจริงโดยไม่บันทึก

### 3.7 เปิดให้ผู้จัดแก้ขั้นหลักบางส่วน (ข้อเสนอ 24 พ.ย. 2026 — รอผู้ใช้อนุมัติ)

ที่มา: ผู้ใช้ถามว่า "step ที่ถูก lock อยู่ถ้าจะให้ผู้จัดสามารถแก้ไขได้ คิดเห็นว่ายังไง" และสั่ง "เขียนลงแผนก่อน" — ยังไม่ลงโค้ด

สถานะปัจจุบัน (พัฒนาแล้ว): ผู้จัดแก้ได้เฉพาะส่วน "ข้อมูลเพิ่มเติมที่ผู้จัดขอ" ในขั้น "ข้อมูล" และขั้นของตัวเอง (สูงสุด 3 ขั้น ระหว่าง "ข้อมูล" กับ "สินค้า") ขั้นหลักอื่นแสดงแบบล็อกในตัวแก้ไข และทุกงานมีขั้น "สรุป" และ "ชำระเงิน" เสมอ

หลักการ: แยก **เนื้อหาและคำถาม** (ผู้จัดแก้ได้) ออกจาก **ตรรกะที่ผูกกับเงิน โควตา สต็อก ตัวตน และ BIB** (ระบบคุม เซิร์ฟเวอร์คำนวณเอง) — ไม่ปลดล็อกทั้งขั้น

| ขั้นหลัก | เสนอให้ผู้จัดทำได้ | ยังล็อก (เหตุผล) |
|---|---|---|
| เริ่ม (เลือกระยะ) | ข้อความแนะนำ, ลำดับการแสดงระยะ | ราคา รอบราคา โควตา — แก้ที่เมนู "ระยะ ราคา และการรับสมัคร" และเซิร์ฟเวอร์กันโควตาแบบ atomic |
| ข้อมูล | (มีแล้ว) เพิ่มคำถาม, ตั้งบังคับตอบช่อง CONFIGURABLE; เพิ่ม: เปิด/ปิดช่องเสริมของระบบ เช่น สัญชาติ ชื่อบน BIB | ชื่อ วันเกิด เพศ ผู้ติดต่อฉุกเฉิน — ใช้คิดกลุ่มอายุ ประกัน BIB รายงาน และการส่งออก |
| สินค้า (เสื้อ/สิ่งที่ได้รับ) | เพิ่มคำถาม เช่น ชื่อสกรีนบนเสื้อ (ไม่มีราคา), ข้อความ/ภาพตารางไซส์ | ไซส์ สต็อก ราคา — กันสต็อกแบบ atomic |
| ของที่ระลึก | ปิดทั้งขั้น, เลือกสินค้าที่แสดงและลำดับ | ราคาและสต็อกสินค้า (จากเมนูร้านค้าของงาน) |
| ที่อยู่ | ข้ามขั้นเมื่อรับอุปกรณ์หน้างานอย่างเดียว (ตามการตั้งค่าการรับอุปกรณ์), เพิ่มคำถาม เช่น จุดรับของ | ค่าส่ง — เซิร์ฟเวอร์คำนวณ |
| สรุป | เพิ่มช่องยอมรับกติกา/waiver ของงาน พร้อมเก็บเวอร์ชันข้อความที่ผู้สมัครยอมรับ (แยกจากการยินยอมการตลาด ตาม AGENTS.md ข้อ 4) | ตัวขั้นสรุป — ผู้สมัครต้องเห็นยอดและรายการก่อนจ่าย |
| ชำระเงิน | ข้อความแจ้งเท่านั้น | ทั้งขั้น — งานฟรีอาจข้ามได้ (ข้อ 8.7) |

ไม่เปิดเลย:
- สลับลำดับขั้นหลัก — ขั้นหลังใช้ผลของขั้นก่อน (ระยะ → ราคา/ไซส์, สินค้า → ต้องกรอกที่อยู่หรือไม่, สรุป → ชำระ)
- เปลี่ยนชื่อขั้นหลัก — ให้เพิ่มคำอธิบายใต้ชื่อแทน ชื่อเดียวกันทุกงานช่วย support และนักวิ่งที่สมัครหลายงาน
- ลบช่องหลักของระบบ — การส่งออก รายงาน และเช็กอินพึ่งช่องเหล่านี้

ลำดับที่เสนอ:
- **รอบ 1:** คำถามในขั้นสินค้า ที่อยู่ และสรุป; ช่องยอมรับกติกาแบบมีเวอร์ชัน; ปิดขั้นของที่ระลึก; ข้ามขั้นที่อยู่ตามวิธีรับอุปกรณ์; คำอธิบายใต้ชื่อทุกขั้น — ใช้กลไกเดิม (`stepKey` ของคำถาม, `normalizeForm`, `validateAnswers`) เพิ่มค่า `stepKey` ของขั้นหลัก และให้หน้าสมัครนักวิ่งแสดงคำถามในขั้นเหล่านั้น
- **รอบ 2:** คำถามคัดกรองในขั้นเริ่ม (เช่น เคยจบมาราธอน แนบผลเวลา) — ต้องมีขั้นอนุมัติ/ปฏิเสธใบสมัคร ซึ่งยังไม่มี

ต้องทดสอบเมื่อลงโค้ด: คำตอบในขั้นหลักตรวจซ้ำที่เซิร์ฟเวอร์, ใบสมัครเก่าผูกเวอร์ชันเดิม, ข้ามขั้นที่อยู่แล้วเซิร์ฟเวอร์ไม่คิดค่าส่ง, เวอร์ชันกติกาที่ยอมรับถูกเก็บกับใบสมัคร, staff/ข้ามองค์กรแก้ไม่ได้

## 4. ส่วน C — ฝั่งนักวิ่งและการใช้คำตอบ

- หน้าสมัครแสดงคำถามตามเวอร์ชันที่เผยแพร่ล่าสุด ตรวจคำตอบบนหน้าจอและตรวจซ้ำที่เซิร์ฟเวอร์
- ข้อความหลังส่งฟอร์มที่ผู้จัดแก้ได้ (ข้อมูลชำระเงินและ BIB ยังมาจากระบบ)
- ผู้จัดดูคำตอบในรายละเอียดผู้สมัคร (ซ่อนข้อมูลอ่อนไหวตามสิทธิ์) และส่งออก CSV/Excel คำถามละคอลัมน์ (เลือกหลายข้อรวมในช่องเดียว)

## 5. ความสามารถจาก Google Forms

### รอบแรก

- การ์ดคำถาม + สวิตช์บังคับตอบ + ทำสำเนา/ลบ (คลิกขวา, Ctrl+D)
- เปลี่ยนประเภทคำถามและเก็บตัวเลือก
- ตัวเลือก "อื่น ๆ (ระบุ)"
- วางหลายบรรทัดเป็นหลายตัวเลือก (มีแล้ว)
- ตรวจคำตอบ รวม "เลือกอย่างน้อย/อย่างมาก N ข้อ"
- หัวข้อ ข้อความอธิบาย และภาพแทรกระหว่างคำถาม (เช่น รูปตารางไซส์เสื้อ แผนที่จุดรับของ)
- อัปโหลดไฟล์ จำกัดชนิดและขนาด
- ดูตัวอย่าง / ลองกรอก
- ข้อความหลังส่งฟอร์ม

### รอบถัดไป

- แสดง/ซ่อนคำถามตามคำตอบข้ออื่น (ไม่ข้ามขั้นตอนหลักของการสมัคร)
- สรุปคำตอบเป็นกราฟต่อคำถาม กดแล้วไปรายชื่อผู้สมัครที่ตอบแบบนั้น
- นำเข้าคำถามจากงานปีก่อนหรืองานอื่นในองค์กร
- แม่แบบฟอร์มตามประเภทงาน (ใช้ `FormTemplate`)
- ประเภทเวลาและสเกลคะแนน
- ลิงก์สมัครที่เลือกระยะหรือโค้ดส่วนลดไว้ล่วงหน้า
- แจ้งผู้จัดเมื่อมีใบสมัครใหม่หรือมีไฟล์ที่ต้องตรวจ
- ผู้สมัครแก้คำตอบเพิ่มเติมได้ถึงวันที่ผู้จัดกำหนด มีประวัติการแก้ (ช่องที่กระทบเงิน ระยะ หรือเสื้อต้องผ่านขั้นตอนเปลี่ยนแปลงเฉพาะ)

### ไม่นำมาใช้ หรือใช้ของระบบเราแทน

| ของ Google Forms | เหตุผล |
|---|---|
| ปิดรับ / จำกัดจำนวนคำตอบ | ใช้ช่วงรับสมัครและโควตาที่กันที่นั่งแบบ atomic |
| เก็บอีเมล / ตอบได้ครั้งเดียว | ใช้บัญชีผู้สมัครและกติกาใบสมัครของระบบ |
| ตารางตัวเลือก (grid) | ซับซ้อนและไม่ค่อยจำเป็นกับงานวิ่ง |
| แบบทดสอบให้คะแนน, สลับลำดับตัวเลือก | ไม่เกี่ยวกับการสมัคร |
| ธีมต่อฟอร์ม | ยังไม่ล็อก design system ใช้หน้าตาของระบบ |
| ผู้แก้ไขร่วมผ่านลิงก์ | ใช้สิทธิ์สมาชิกองค์กร |

## 7. การทดสอบที่ต้องมี

- ข้ามองค์กร: แก้หรืออ่านฟอร์มของงานอื่นไม่ได้
- เผยแพร่ฟอร์มใหม่ระหว่างที่มีคนกำลังสมัครด้วยเวอร์ชันเดิม — ใบสมัครเดิมผ่านตามเวอร์ชันเดิม
- ใบสมัครเก่ายังเปิดดูคำตอบได้ครบหลังเปลี่ยนฟอร์ม
- คำถามบังคับตอบที่ซ่อนตามเงื่อนไขไม่บล็อกการส่ง
- ลบ/เปลี่ยนประเภทคำถามที่มีคนตอบแล้วถูกปฏิเสธที่เซิร์ฟเวอร์
- คำถามข้อมูลอ่อนไหวเผยแพร่ไม่ได้ก่อนอนุมัติ และ staff ไม่เห็นคำตอบ
- แปลงข้อความหน้าแบบ v2 กลับลงข้อมูลงาน (กรณีปกติ, กรณีผู้จัดเปลี่ยนโครง, ร่างที่ไม่เผยแพร่)

## 8. เรื่องที่ต้องตัดสินใจ

1. คิวคำขอเพิ่มฟิลด์ถึง Platform Owner (ข้อ 17.3) ยังใช้สำหรับเพิ่มฟิลด์เข้าคลังกลาง หรือเลิกใช้ เพราะผู้จัดสร้างคำถามเองได้แล้ว (เสนอ: ใช้ต่อเฉพาะคำถามข้อมูลอ่อนไหว) — **ตัดสินบางส่วนแล้ว 24 พ.ย. 2026 (ผู้ใช้สั่ง "เอาแม่แบบเครื่องมือเดิมออก"):** ฝั่งผู้จัดเอาเครื่องมือเดิม (เลือกแม่แบบฟอร์มของแพลตฟอร์ม + ส่งคำขอเพิ่มช่อง) ออกแล้ว ผู้จัดสร้างคำถามเองในเมนู "ฟอร์มสมัคร" อย่างเดียว ส่วนคิวคำขอและคลังแม่แบบในคอนโซลแพลตฟอร์มยังอยู่ — ยังไม่ตัดสินว่าจะเลิกหรือเปลี่ยนเป็นที่อนุมัติคำถามข้อมูลอ่อนไหว
2. ข้อความ "เกี่ยวกับงาน / สิ่งที่ได้รับ / กำหนดการ" และการ์ดสมัครอยู่เมนูใดในระบบผู้จัดใหม่ (ให้สอดคล้องกับ redesign navbar)
3. คงการตั้งค่าการ์ดสมัคร (หัวการ์ด โปรโมต มาสคอต) ไว้หรือไม่
4. เงื่อนไขแสดงคำถามตามคำตอบข้ออื่น อยู่รอบแรกหรือรอบที่ 2 (เสนอ: รอบที่ 2)
5. ผู้สมัครแก้คำตอบหลังส่งได้หรือไม่ และถึงเมื่อไร
6. เพิ่มประเภทเวลาและสเกลคะแนนหรือไม่
7. งานฟรี (ยอด 0 บาท) ข้ามขั้น "ชำระเงิน" หรือไม่ (เสนอ: ข้ามขั้นชำระเงิน แต่คงขั้นสรุปไว้ยืนยันก่อนส่ง) — ถามผู้ใช้แล้ว 24 พ.ย. 2026 ยังไม่ได้คำตอบ
8. อนุมัติข้อเสนอข้อ 3.7 (เปิดให้ผู้จัดแก้ขั้นหลักบางส่วน) และขอบเขตรอบ 1 หรือไม่
